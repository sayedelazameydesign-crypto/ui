# بروتوكول التحسين الحتمي والتحقق الصارم
# Deterministic Optimization & Verification Protocol

> **الحالة:** البروتوكول معتمد؛ تنفيذ محرك التحسين لم يبدأ.
> **النطاق:** أي تحليل أو سير عمل يتخذ قراراً رقمياً/تشغيلياً اعتماداً على هدف وقيود صريحة.
> **القرار المعماري:** [ADR-0025](../adr/0025-deterministic-optimization-and-verification.md).

## 1. الهدف والمبدأ

يفصل البروتوكول بين الفهم الاحتمالي والقرار الرياضي الحتمي والتحقق المكتوب بقواعد عادية. لا يجوز اعتبار ناتج نموذج لغوي حلاً رقمياً معتمداً أو استخدامه مباشرةً في التسعير أو توزيع الموارد أو الجدولة أو تنفيذ عملية ذات أثر مالي/تشغيلي.

المسار المقصود:

```text
وصف المستخدم
    ↓
LLM اختياري: اقتراح صياغة مهيكلة + إظهار الافتراضات والأسئلة
    ↓ موافقة/تصحيح بشري عند الغموض أو الأثر العالي
عقد بيانات محدود ومتحقق منه (Objective, Variables, Constraints)
    ↓
مراجعة قبل الحل → Solver محلي/محدد الإصدار → تحقق مستقل بعد الحل
    ↓ فقط إذا اجتاز التحقق
نتيجة رقمية معتمدة + تفسير بشري مقروء
```

يجوز إدخال العقد يدوياً؛ لا يعتمد تشغيل الـ Solver على توفر LLM أو اتصال بالشبكة. النموذج اللغوي مترجم/مساعد صياغة ومفسر للنتائج، وليس جهة صلاحية لاتخاذ القرار.

## 2. فصل المسؤوليات

| المكوّن | المسؤولية المسموحة | ما لا يملكه |
|---|---|---|
| مُدخل الطلب / LLM اختياري | اقتراح الحقول والقيود بصيغة بيانات، كشف النواقص، صياغة تفسير للنتيجة المعتمدة | لا يحسب حلاً معتمداً، ولا يخفف قيداً، ولا يخترع قيمة افتراضية صامتة |
| عقد المسألة / المحلل | التحقق من البنية والأنواع والوحدات والمجالات، وتحويل الأنواع المسموحة إلى تمثيل داخلي محدود | لا يقبل شيفرة أو تعبيرات تنفيذية أو مفاتيح غير معروفة |
| محرك التحسين | حل نموذج رياضي معلوم ومحدود وفق هدف وقيود معتمدة | لا يفسر لغة طبيعية ولا يختار افتراضات أعمال |
| بوابة التحقق | إعادة تقييم القيود والهدف من المدخلات الأصلية والحل؛ رفض أي نتيجة غير صالحة أو غير مؤكدة | لا تصلح الحل ولا تتساهل مع فشل أو تجاوز صامت |
| العرض / LLM اختياري | عرض أرقام معتمدة كما هي وشرح معناها مع الإشارة إلى الوحدات والقيود | لا يعدل الأرقام المعتمدة أو ينشئ أرقاماً مشتقة غير محسوبة ومتحققاً منها |

## 3. عقد المسألة

كل مسألة قابلة للحل تصف، على الأقل:

1. **الهدف:** تعظيم أو تقليل دالة محددة، مع الوحدة ومعنى كل معامل.
2. **متغيرات القرار:** الاسم والنوع (مستمر/صحيح/ثنائي)، الوحدة، والحدود المسموح بها.
3. **القيود:** تعبيرات من مجموعة عمليات معتمدة، العلاقات المسموحة، الوحدات، الحدود ومصدرها.
4. **بيانات المسألة:** قيمة كل معامل ومصدره/تأكيد المستخدم؛ لا تُستنتج القيم الناقصة بصمت.
5. **إصدار العقد والسياسة:** لتفسير النتائج وإعادة تدقيقها.

يُقبل JSON وفق مخطط صارم ومحدود؛ الحقول الزائدة والأنواع غير المتوافقة والوحدات غير المتسقة والقيم غير المنتهية أو الخارجة عن النطاق تُرفض. لا تُقبل Python أو DSL حر أو SQL أو AST تنفيذي، ولا `eval()` أو `exec()`، ولا توليد شيفرة من LLM.

عند غموض مؤثر، يعرض النظام أسئلة وافتراضات للمستخدم ويتوقف عن الحل حتى التأكيد. عند تناقض البيانات أو القيم غير الممكنة، يفشل الفحص قبل استدعاء المحرك.

## 4. بوابتان إلزاميتان للفشل الآمن

### قبل الحل — Pre-solve

- التحقق من المخطط والإصدار والحقول والوحدات والمجالات والحدود.
- رفض NaN/Infinity، الحدود المعكوسة، المعاملات المفقودة، العمليات غير المدعومة وأحجام المسألة التي تتجاوز الحدود المعتمدة.
- اكتشاف التناقضات المباشرة حيثما أمكن؛ لا يُفترض أن كل مسألة ممكنة قبل حلها.
- عدم استدعاء solver إذا فشل أي تحقق. لا تُسقط القيود ولا تحوّلها إلى soft constraints تلقائياً.

### بعد الحل — Post-solve

- لا تُقبل حالة solver إلا إذا كانت `optimal` وفق معيار موثق؛ حالات infeasible وunbounded وtimeout وunknown وerror لا تنتج قراراً معتمداً.
- إعادة حساب قيم الهدف والقيود باستخدام كود تحقق مستقل عن مسار بناء النموذج/الحل، وبمدخلات المسألة الأصلية.
- التحقق من حدود المتغيرات والتكامل/الثنائية والوحدات وحدود الخطأ العددي المعتمدة. إذا فشل أي فحص، تُرفض النتيجة ولا تعرض كقرار.
- عند عدم وجود حل صالح، اشرح حالة الفشل واطلب من المستخدم تعديل قيد بعينه؛ لا يرخّي النظام القيد ولا يقترح حلاً غير صالح.

مصطلح «حتمي» يعني أن نفس العقد وإصدار المحرك وإعداداته تنتج نتيجة قابلة لإعادة الإنتاج ضمن ضمانات المحرك المحددة؛ لا يعني دقة مطلقة 100% لكل مسائل الأعداد الحقيقية. لكل solver حدود دقة وتسامح وعدّاد إنهاء، ويجب توثيقها واختبارها. لا تُعرض قيمة «مثلى» دون شهادة حالة optimal والتحقق المستقل.

## 5. العرض وسجل التدقيق

- لا تبدأ صياغة التقرير إلا من نتيجة اجتازت بوابة التحقق. الأرقام والموارد المستخدمة والمتبقية وحساب المكسب تأتي من بيانات مشتقة آلياً ومتحقق منها؛ النص التفسيري لا يغير المصدر الرقمي.
- يسجل سجل تدقيق قابل للمراجعة: بصمة/نسخة عقد المسألة، نسخة المحرك وإعداداته، حالة الحل، النتيجة، تفاصيل التحقق، والوحدات والتوقيت. تحفظ المدخلات النصية الخام فقط وفق موافقة واحتفاظ/خصوصية محددين؛ لا تُسجل الأسرار أو بيانات شخصية غير لازمة.
- قاعدة البيانات المحلية (مثل SQLite) خيار تنفيذ مقترح، لا اختيار معتمد بعد. يلزم تحديد سياسة حذف واحتفاظ وحماية ونسخ احتياطي قبل تخزين بيانات تشغيل حقيقية.
- يعمل حل المسألة وعقدها المحليان دون شبكة. أي LLM سحابي يكون اختيارياً ويتطلب موافقة صريحة ووجهة معلنة؛ انقطاعه لا يمنع إدخال العقد يدوياً أو حلها محلياً.

## 6. خارطة التنفيذ المرحلية

| المرحلة | التسليم | بوابة القبول |
|---|---|---|
| 0. تحديد المجال | دراسة حالة أعمال واحدة، وحداتها، المعاملات، ومصدر كل قيد؛ قائمة حالات الفشل والآثار المالية | لا قيم مجهولة ولا ادعاء أن مثال الفيديو قابل لإعادة الإنتاج قبل توثيق كل معاملاته |
| 1. عقد البيانات | مخطط إصدار أول + أنواع متغيرات وقيود مدعومة + مدقق fail-closed | اختبارات إيجابية وسلبية، مدخلات زائدة/ملتبسة مرفوضة |
| 2. نموذج المجال | تمثيل داخلي محايد للمحرك ووظائف pure لبناء الهدف والقيود | لا تفسير أو تنفيذ لكود مقدم من النموذج؛ وحدات وحدود مفحوصة |
| 3. اختيار المحرك | مقارنة تجريبية صغيرة لمكتبات مفتوحة المصدر مناسبة للقيود المحددة، الإصدارات والرخص والتشغيل offline | ADR منفصل يقارن البدائل على مسائل اختبار؛ لا اعتماد مكتبة قبل القرار |
| 4. المحرك | واجهة حل محلية، مهلات/حدود موارد، حالات خروج صريحة، نتيجة موحدة | ثابتة الإصدار والإعداد، بلا شبكة أو مفاتيح، اختبارات حتمية للمسائل الصغيرة |
| 5. بوابة التحقق | تقييم مستقل للهدف والقيود والحدود العددية | اختبارات طفرة/اختبارات خصائص تثبت رفض خرق القيد، حالة غير مثلى، وقيم غير صالحة |
| 6. التدقيق والتفسير | سجل محدود البيانات + تقرير يعرض الحل والموارد المتبقية وحالة التحقق | أرقام العرض تطابق النتيجة المعتمدة؛ النص لا يستطيع تغيير قيمها |
| 7. دمج اختياري مع LLM | مُدخل/مفسر ينتج اقتراح عقد فقط؛ الإدخال اليدوي يبقى متاحاً | مقارنة الاقتراح بالعقد بعد التحقق، موافقة عند الغموض، اختبار انقطاع LLM |

**تسلسل تقريبي للمسارات:** لا تسبق المرحلة 0 بإضافة تبعية. يمكن بناء مدقق العقد والتحقق المستقل على مكتبة قياسية أولاً، ثم إجراء ADR للمحرك، ثم تنفيذ نطاق مسألة واحد. لا يبرر البروتوكول اختيار Python أو PuLP أو SciPy أو OR-Tools قبل دراسة متطلبات المجال وإصدار ADR.

## 7. مثال المصنع ومتطلبات البيانات

المرجع المقترح للاختبار هو مصنع بمنتجين، و60 ساعة عمل، و50 كغم من المواد الخام. لا تكفي هذه الأرقام وحدها لحساب نتيجة 12,400 جنيه أو التحقق منها. يجب توفير، لكل منتج، ربح الوحدة، ساعات العمل لكل وحدة، كمية الخام لكل وحدة، حدود الطلب/الإنتاج، وأي شروط إضافية؛ كما يجب توضيح ما إذا كان الهدف إجمالي الربح أو صافي الربح وأي تكاليف داخلة فيه.

إلى أن توثق هذه القيم من المصدر، تسجل `12,400 جنيه` كقيمة مرجعية غير متحققة، لا كاختبار قبول ولا كحقيقة عن مخرجات المحرك. بعد اكتمال البيانات، تحفظ كحالة اختبار اصطناعية موثقة وتتحقق النتيجة مستقلاً بحساب يدوي/حل صغير معروف.

## 8. معايير القبول قبل استخدام تشغيلي

- لا يمكن لـ LLM أو المستخدم تمرير كود أو إلغاء بوابة التحقق.
- كل قيمة قرار رقمية يمكن ردّها إلى متغيرات وعقد معتمد ونسخة solver.
- حالات الفشل وعدم اليقين والمهلة والتناقض ترفض القرار fail-closed وتشرح الإجراء التالي دون اختلاق حل.
- مدخلات يديوية وحل محلي يعملان دون اتصال أو مفتاح API.
- اختبارات تغطي مخططات غير صالحة، القيود المكسورة، infeasible، unbounded، timeout، حدود التقريب، إعادة الإنتاج، ومطابقة العرض للأرقام المعتمدة.
- أي مجال مالي أو عالي الأثر يحتاج مراجعة بشرية، تحقق مستقل مناسب، وحدود تشغيلية موثقة قبل تفعيل القرار الآلي.

## 9. ما لم يُحسم

لا يختار هذا البروتوكول مكتبة أو لغة تنفيذ أو قاعدة بيانات، ولا يجيز إجراء معاملات فعلية أو تحديث أسعار/مخزون/جداول تلقائياً. تتطلب هذه الاختيارات ADRs وبيانات مجال مكتملة واختبارات قبول منفصلة. النسخة الحالية من منشئ المواقع تظل تخطيطاً فقط ولا تملك محرك تحسين.
